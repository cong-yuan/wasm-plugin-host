# 路线图 — 用 WASM 插件复刻 dsh-web 的功能面

> 目标：做一个 WASM 插件宿主 + 对应 Web，**功能面覆盖 dsh-web**；
> 差异点：**后加载的插件可以改造已有 UI**（隐藏/重排/替换）——
> 注意 `dsh-web` 有**移动端 CSS 抑制**（6 个硬编码插件名，仅隐藏）；
> 我们的不同在机制（注册表 vs CSS）与广度（glob + 四动作 + 可逆），不是"有无"。
>
> 本文是差距分析与推进顺序。**先说清楚现状，再说要做什么。**

## 0. 现状（诚实版）

我们现在有什么：

| 已有 | 说明 |
|---|---|
| WASM 宿主 | wasmtime + WASI p1，磁盘编译缓存（冷启 ~36x） |
| ABI v1 | JSON 过线性内存；9 个导出 + 7 个宿主导入 |
| 服务图 | `provides`/`injects`，响应式收敛，cordis fiber |
| 前端槽位 | `SlotRegistry`，顺序无关/响应式/冲突报错 |
| **UI 改造层** | **`ui.adjusts`：hide / unhide / replace / priority** ← 注册表级,比 dsh-web 的 CSS 抑制更宽 |
| 多窗口 | 插件可开顶层窗口；独立 HTML 页模式；窗口传参 |
| 桌面端 | Tauri 2 + Svelte 5，插件持久化 + 热重载 |
| 管理界面 | 插件列表、槽位图、调整面板 |

我们**没有**什么（相对 dsh-web）：

| 缺 | 影响 |
|---|---|
| **任何功能插件** | 只有 3 个 UI demo，**零实际功能**。这是最大差距 |
| 插件内共享层 | 宿主侧与前端侧的逻辑各写一遍 |
| i18n | 文案中英混排，无门禁 |
| 遥测/统计 | 无 |
| 设置卡体系 | 插件直接改配置，无暂存/原子提交/读回 |
| 插件管理（安装/更新） | 只有本地 `.wasm` 扫描 |
| 主题/皮肤 | 无资产分发机制 |
| 会话归档、SSH、Git 图谱等功能 | 全无 |

**关键结论：dsh-web 的体量是 ~9068 文件、21 个包、@7600 star。**
我们在"宿主能力"上领先（WASM 边界、热重载、UI 改造层），
在"功能供给"上接近零。**路线图的重点必须是功能，不是继续打磨宿主。**

## 1. 复刻的四个层次

不是所有功能都同等地难。按**宿主必须先具备的能力**分四层：

### L1 — 纯前端功能（当前就能做）

插件只需要：注册组件 + 写 DOM + 用 `host.http_fetch` 发请求。

| dsh-web 对应 | 我们怎么做 | 难度 |
|---|---|---|
| `dsh-usage`（token 用量、余额） | `entry.js` + `http_fetch` + 图表 | 低 |
| `dsh-model-capabilities`（模型能力声明编辑器） | 表单 + 写配置 | 低 |
| `dsh-session-id` | 显示会话 id | 低 |
| `dsh-pet`（桌面宠物） | 纯 DOM + 动画 | 低 |
| 皮肤/主题（CSS 注入） | `style.css` 资产（已有通道） | 低 |
| `dsh-skill-explorer` | 列表 + 预览 | 低 |

**这一层现在就能开工，不需要动宿主。** 它也是验证"插件开发体验"是否够用的最好方式——
如果写三个 L1 插件很痛苦，那是 DX 问题，该先修 DX。

### L2 — 需要宿主补能力

| dsh-web 对应 | 缺什么 |
|---|---|
| `dsh-task-board`（任务看板 + cron） | **定时器**：宿主需要在指定时刻唤醒插件 |
| `dsh-session-archive`（会话归档） | **会话读写**：插件需访问 dsh 会话存储 |
| `dsh-git-graph`（Git 图谱） | **进程执行**：要跑 `git`（或纯解析 `.git`） |
| `dsh-ssh`（SSH 终端） | **网络 + 长连接 + 终端模拟**（WASI p1 无 socket，需宿主代理） |
| `dsh-remote-web-ui`（手机远程） | **HTTP 服务端**：宿主需开监听端口 + SSE |
| `dsh-doctor`（自检） | 一般性诊断 API |

**这一层的共同点：插件需要"宿主替它做它做不到的事"。**
WASI p1 没有 socket、没有进程、没有定时器。
**我们的 `host.http_fetch` 已经是这个模式的第一个实例**——把它推广成一套
"宿主能力"接口（`host.*`），是 L2 的前置工作。

### L3 — 需要平台级能力

| dsh-web 对应 | 缺什么 |
|---|---|
| `dsh-plugin-manager`（安装/更新/启用） | **包管理**：下载、校验、依赖、回滚 |
| `dsh-market`（创意工坊） | **分发**：manifest、签名、版本、索引 |
| `dsh-preset-center` | **数据分发** + 惰性库 |
| `dsh-web-all`（聚合包） | **组合机制** |

**这一层决定生态能否形成。** 但它的前提是 L1/L2 有足够多的插件值得分发——
顺序上应该靠后。**过早做市场会得到一个空市场。**

### L4 — 我们的差异点（dsh-web 只在移动端用 CSS 抑制做过"隐藏"）

| 能力 | 状态 |
|---|---|
| 隐藏别人的贡献 | ✅ 已实现 |
| 重排别人的贡献 | ✅ 已实现 |
| 替换别人的组件 | ✅ 已实现 |
| **以调整构建整套"预设布局"** | ⬜ 未做：一组调整 = 一个命名预设，可切换 |
| **调整的可视化编辑** | ⬜ 未做：现在的调整只能写在 WASM 里 |
| **调整的审计/冲突检测** | ⬜ 未做：两个插件调整同一目标时，目前后者静默胜出 |

**L4 是产品的差异点，应该和 L1 并行推进**——因为 L4 的价值要靠 L1 的插件来证明
（有东西可调整，调整才有意义）。

## 2. 建议顺序

```
现在 ──┬─► ① DX 修补（见第 3 节）        ← 半周
       │
       ├─► ② L1 功能插件 × 3             ← 这两步一起验证"够不够用"
       │     dsh-usage 等价（http_fetch + 图表）
       │     主题/皮肤（style.css 通道）
       │     一个纯 DOM 小工具
       │
       ├─► ③ L4 补完：预设布局 + 冲突检测  ← 把差异点做成产品
       │
       └─► ④ L2 宿主能力推广              ← 定时器 / 会话 / 进程 / HTTP 服务端
             然后才是 ⑤ L3 分发
```

**为什么 DX 排在功能前面**：dsh-web 的插件是 npm 包 + TS，开发体验是一等的。
我们的是"Rust 里塞一段 JS 字符串"，写第二个插件时就会痛。
**在痛之前修，比痛之后修便宜。**

## 3. 第①步：DX 修补 —— **已完成**

来自 [`借鉴-dsh-web-模式.md`](借鉴-dsh-web-模式.md) 的结论。**注意：先探测再动手。**
探测结果推翻了最初的两项判断（见下），且找到了两个原计划里没有的真 bug。

| # | 做什么 | 状态 | 验收 |
|---|---|---|---|
| 1 | 双源加载防重 | ❌ **探测后判定为非真问题** | 见下 |
| 2 | disposer 带 label | ✅ 完成 | `PluginHandle.track(label, run)`，日志含来源 |
| 3 | 批量挂载容错 | ✅ 完成 | 一个抛错的组件不再中断同槽位其余贡献，且不留孤儿节点 |
| 4 | 组件可写成独立文件 | ✅ 完成 | `studio.require(name)`，多资产、可嵌套、懒加载 |
| 5 | 插件内共享层 | ⏸ 仍推迟 | （需设计） |
| + | **热重载泄漏**（原计划未列） | ✅ 完成 | 见下 |
| + | **teardown 隔离**（原计划未列） | ✅ 完成 | 一个 teardown 抛错不中断其余 |

### 为什么第 1 项没做

我本打算照搬 dsh-web 的 `globalThis` 防重标志。**动手前先写了探测，结果复现不出它要解的问题**：

- `openSlot` 对同一 owner 是幂等的（重复 `provides` 不报错、不重复）
- `executed` 映射已经去重了并发 `sync()`（三次并发调用只跑一次 `entry.js`）
- 宿主是单例，不存在 dsh-web 那种"同一包作为两个模块实例加载"的场景

**所以没加。** 加一个对空气的守卫比不加更糟——它会在将来掩盖真实的重复注册。
这个判断记录在此，以免以后又想起来加。

### 探测却找到了两个真 bug（原计划里没有）

**① 热重载泄漏 imperative claims。** `PluginHandle.dispose()` 清了 factories 和 slotTargets，
但**漏了 `studio.inject(...)` 注册的 claims**；而 `runEntry` 在 `entry.js` 每次变化时都会重跑。
实测一个真实的重载序列：claims 从 1 → 3 → 4，**永远降不回来**。
现已改为带 label 的 teardown 列表（新→旧执行，逐个隔离）。slot 容器的刷新闭包同样泄漏，一并修了。

**② 一个抛错的组件会清空整个槽位。** `mount()` 让 factory 的异常逃逸出去，
而 `<Slot>` 用 `list.map(...)` 挂载贡献——第一次抛错就中断整个循环，
**同槽位后面所有贡献都不渲染**。已改为容错并移除孤儿 wrapper（失败表现为一个空缺，而非未追踪节点）。

这两个都是**我们自己架构里的缺陷**，不是从 dsh-web 搬来的。

### 第 4 项（多文件插件）现在长这样

```json
"assets": {
  "lib/dom.js": "return { h: (tag) => document.createElement(tag) };",
  "panels.js":  "const { h } = studio.require('lib/dom'); …",
  "entry.js":   "studio.require('panels'); studio.inject('settings.tabs', 'Panel', 10);"
}
```

懒加载、缓存、可嵌套、循环报错、未知名报错并列出可用名。
**关键细节**：只改模块（不动 `entry.js`）也会重跑 entry，
因为注册闭包捕获了模块的返回值——否则改 helper 会"看起来没生效"。
实例见 `plugins/ui-multifile`（`entry.js` 三行 + 三个模块）。

**L1 插件的 DX 障碍已清除，可以开始写真插件了。**

## 4. 第③步：L4 补完（差异点产品化）

现在 `ui.adjusts` 是**声明式**的。要变成产品，还差三件：

### 4.1 调整预设（"布局"）

一组调整 = 一个命名预设，用户可切换、可分享。

```jsonc
"ui": {
  "layouts": [
    { "name": "focus",  "adjusts": [ /* 隐藏次要面板 */ ] },
    { "name": "debug",  "adjusts": [ /* 全部展开 + 重排 */ ] }
  ]
}
```

用户选 `focus`，则应用该组；切换即换组。
**这直接来自我们的"可逆"性质**——丢弃一组调整就回到声明态。

### 4.2 调整的可视化编辑

现在只能改 WASM 重新编译。应能在 UI 上：
勾选隐藏某贡献、拖拽排序 → 导出为一段 `adjusts` JSON。

### 4.3 冲突检测

两个插件都调整 `settings.tabs` 时，现在**后者静默胜出**。应该：
- 在槽位图里标出"此处有 N 个调整，最终由 X 决定"
- 提供显式的覆盖顺序（而不是仅靠加载顺序）

**参考 `dsh-web` 的“契约归属”纪律**。他们的语义属性契约写得很明白：

> 契约归属：本表由皮肤中心单方面拥有和维护（**冲突仲裁纪律：不靠加载顺序**）。

他们把**所有权**作为仲裁依据，而不是让"谁后加载"决定。我们可以借这个思路：
给一段 UI （一个 slot 或一组贡献）定一个**仲裁者**，
多个调整竞争时由仲裁者决定，而非靠加载顺序——
这与我们已有的"slot 名冲突就报错"是同一套精神，只是从“名字”扩到了“内容”。

还有一个**立即能改的点**：我们现在已经有 `data-plugin` / `data-slot` /
`data-rendered-by` 三个 DOM 属性（为了测试而写），但没有当公开契约。
`dsh-web` 的脆弱点清单第 4 条正是"list slot 的单 entry 无 DOM 归属标识"——
**我们白得了这个能力，却把它当内部实现**。应把它文档化、版本化、声明归属，
否则插件键上去、我们又无意中改它，就会碎。

**这一条与我们的"冲突报错"原则一致**——slot 名冲突是报错的，
调整冲突也应该可见。目前的静默是**不一致的**。

## 5. 不做什么

| 不做 | 为什么 |
|---|---|
| 复刻 dsh-web 的 MutationObserver 注入 | 我们有槽位注册表，那是他们的妥协 |
| 照搬 `SlotMap` 类型化槽位 | 前提（编译期槽位名）在我们这里不成立 |
| Electron + 内置 Node | 与 WASM 沙箱边界相悖 |
| 先做市场/分发 | 空市场没有价值；先有值得分发的插件 |
| 无沙箱的信任模型 | dsh-web 是"信任 TS"，我们有 WASM 边界——**这是优势，不该放弃** |

**最后一条要强调**：`docs/已知问题.md` §1.1 记录了"可信插件、最大权限"的产品决策。
那是**当前的**选择，不是架构限制。WASM 边界意味着将来可以**收窄**到真沙箱，
而 dsh-web 的 TS 插件永远做不到。**这是我们的结构性优势，路线图不应把它消耗掉。**

## 6. 里程碑验收

| 里程碑 | 完成标志 |
|---|---|
| **M1 — DX** | 能写一个 L1 插件而**不需要把 JS 塞进 Rust 字符串**，且不需要读宿主源码 |
| **M2 — 功能** | 3 个真能用的 L1 插件，不是 demo |
| **M3 — 差异** | 用户能在 UI 上组出一套布局（调整预设），一键切换，且切回原状 |
| **M4 — 平台** | 一个插件能安装另一个插件（分发闭环） |

**M2 之后再谈 M3/M4 的具体设计。** 现在最缺的不是架构，是第一个真正有用的插件。
