# 前端可塑性审计

> 回答：**"前端可以任意修改"现在到哪一步了？还差什么？**
> 依据：`dsh-wasm-studio` 源码实测（只读审计）。

## 结论先行

**"换整站皮肤"今天就能做**（零 Rust 改动），只是没测过。
真正缺的是**插件贡献路由与菜单**——两者都很小。

## 1. 已经可用的（不需要新代码）

| 能力 | 通道 | 状态 |
|---|---|---|
| 往壳里填块 | `Slot` + 5 个内置槽位 | ✅ |
| 开独立窗口 | `ui.windows`（app / html 两种） | ✅ |
| 整站换色 | 插件 `style.css` 覆盖 CSS 变量 | ✅ **已测** |
| 改写别人的 UI | `ui.adjusts`（hide/unhide/replace/priority） | ✅ |

### 为什么"换整站皮肤"已经能用

三个事实叠起来：

1. **主题已 100% token 化**。实测 `var(--…)` **116 处**，硬编码 hex **仅 1 处**。
   所有颜色走 `:root` 上的自定义属性（`src/lib/theme.css`）。
2. **插件样式运行时追加到 `head`**（`plugin-host.ts:524` 的 `ensureStyle`），
   而内置样式是构建产物里的 `<link>`（`index.html`，解析时即生效）。
3. 同为 `:root` 的单特异性选择器，**文档顺序在后者胜** →
   运行时追加的插件样式**覆盖内置**。

且 `plugin-host.ts` 是**唯一**在运行时往 `head` 插样式的地方（已 grep 确认，
Svelte 组件自身不这么做），所以没有竞争者会打乱顺序。

```css
/* 一个插件的 style.css：零 Rust 代码，换掉整站配色 */
:root {
  --bg-canvas: #000;
  --accent: #7c3aed;
}
```

**已写测试证明**（`plugin-host.test.ts` 的
"a plugin's style.css replaces the app's theme tokens"）：样式确实进了 `<head>`、
带 `data-plugin-style` 归属、重载时**原地更新**（不会在 head 里堆积）、
卸载时移除。

**写这个测试时抓到一个真 bug**：`release()` 的清理循环原本遍历 `handles`，
但**只有 `style.css`、没有 `entry.js` 的插件根本不会建 handle** —— 于是
卸载它时样式**留在 `<head>` 里**，旧主题位置靠后、继续胜出。
已改为由"上次同步见过的 owner 集合"驱动清理。

## 2. 真正缺的两块

### 2.1 插件贡献路由

- 现状：`src/routes/` 是**硬编码目录**（8 个页面），**动态路由 0 个**。
- 缺：一个 catch-all 路由（`[...plugin]`），把未知路径交给插件。
- **基础设施已具备**：`adapter-static` + `fallback: "index.html"` + `ssr = false`
  （`src/routes/+layout.ts`），本来就是 SPA，任意路径都能落到前端。
- 成本：**小**。

### 2.2 插件贡献菜单

- 现状：`src/routes/+layout.svelte:30` 是硬编码的 `const nav = [...]`，8 条。
- 缺：把 `nav` 变成"内置项 + `nav.items` 槽位"，让插件注入条目。
- 成本：**小**（`sidebar.items` 槽位已有先例）。

## 3. 不需要做的：主壳插件化

曾以为"换皮肤 / 加整页"必须先"把主壳降为可替换壳"。**实测不成立**：

- 换皮肤：见 §1，已可做。
- 加整页：见 §2.1，一个 catch-all 路由即可。
- 加菜单项：见 §2.2，一个槽位即可。

**主壳插件化**（壳自己成为插件）是最后的形态，不是前提。理由：

1. 它要改写 Svelte 的路由与布局，是**侵入式重构**，风险最高；
2. 它换来的东西，上面两小块已经用更小代价拿到；
3. **dsh-web 自己也没这么做**——他们的 Chat 与侧栏**始终是宿主 React**，
   插件靠 `data-dsh-plugin` 语义属性 + CSS 打补丁，而不是接管主壳
   （见 [`对比-dsh-web.md`](对比-dsh-web.md)）。

## 4. 与流程侧的关系

| | 流程侧 | 前端侧 |
|---|---|---|
| 天花板 | dsh-rs 只开 6 个 waterfall 点 | 无硬上限（前端全在我们手里） |
| 现状 | 3/6 | 填块/开窗/改造✅，路由/菜单❌ |
| 下一步 | 补满 6/6 | `nav` 槽位 + catch-all 路由 |

**前端侧比流程侧自由**：流程受限于 dsh-rs，前端受限于我们自己写的代码量。
所以"任意修改前端"是**更可达**的那个目标。

详见 [`dsh-rs-扩展面.md`](dsh-rs-扩展面.md)。
