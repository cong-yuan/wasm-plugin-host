## 一、严重(会影响使用决策)

### 1.1 能力模型:**明确采用"可信插件、最大权限"** 🟡【产品决策】
- **决策(已定)**:插件是**受信的**,默认给**最大权限**。这不是疏忽,是选择。
- **实现现状**:
  - **文件系统**:`/` 整个根预打开(读写)—— 插件能读写宿主能碰的任何文件。
  - **网络**:WASI p1 的 `sock_*` 在 wasmtime 44 里是**未实现的 stub**
    (`bail!("sockets are not currently supported")`),所以网络只能走
    **`host.http_fetch`**(宿主用 ureq 代发,返回 `{status, headers, body}` JSON)。
  - **宿主导入**:`log / now_ms / get_config / config_version / call_service /
    has_service / http_fetch`。
- **影响**:**不能安全运行第三方不可信插件**。只适合"自己写的、可信的"插件。
  - 一旦插件能在 webview 里跑 JS(前端插件),它能调所有 Tauri 命令、
    读 `studio.json`(含 API key)、直连外网 —— 沙箱不再存在。
- **将来若要支持不可信插件**:需要回头做 P0 —— preopen 白名单 + fuel +
  内存上限 + `permissions` 配置;`http_fetch` 要加域名白名单。
  见 [计划.md](计划.md) P0。

### 1.2 `Store` 非 `Sync`(设计约束,非 bug)
- **现象**:一个 `Store`(及其 `Instance`)同一时刻只能被一个线程使用。
- **事实澄清**:`Store<T>` **是 `Send`**(可跨线程移动),**不是 `Sync`**(不能多个线程同时用)。已用代码实测确认。
- **后果**:
  - 一个插件实例**不能并发调用** —— 同一 slot 的调用被串行化。
  - 不同 slot 可以并行(已经这样做了,见 `call_many_parallel`)。
- **为什么**:这是 wasmtime 的设计(实例内部状态非线程安全)。
- **怎么办**:要更高并发就**同一插件多开几个实例**(不同 slot),或按 slot 分片到线程。
  池化分配器让多实例很便宜。
- **这条现在是规范**:ABI 文档的 “Threading” 一节把**每实例不重入**写成了契约,
  并用 `dsh-wasm-host/tests/serialization.rs` 钉住(4 个测试:同 slot 不重叠、
  跨 slot 可并行且同实例仍不重叠、`WasmHost` 全局串行、hook 在锁内被调)。
  它以前只是 `Store` 非 `Sync` 的**副作用**,没人写下来也没人测 —— 于是「按插件(而非
  按 slot)复用实例」这类改动会**静默**把每个插件的 global 变成数据竞争。

### 1.3 `LogHook` 不能回调 `WasmHost`(设计约束,非 bug)
- **现象**:在 `LogHook` 里调 `host.list_plugins()` 之类的 `WasmHost` 方法会**自死锁**。
- **为什么**:`WasmHost::call_tool` 为**整个** guest 调用持有 registry 锁;而 guest 的
  `host.log` 在**该调用内部**触发 hook。锁不可重入,于是同一线程第二次 `lock()` 挂死。
- **注意区分**:这**不**限制 guest 之间互相调用 —— `host.call_service` 是可行的,
  因为它把被调者**从 store 取出**而不是通过那把锁去够(见 ABI 的 Re-entrancy 一节)。
- **怎么办**:hook 里只做「收下 → 丢进 channel → 返回」。不要同步回调宿主。
- **实测**:`dsh-wasm-host/tests/serialization.rs` 里
  `the_log_hook_runs_while_the_registry_lock_is_held` 用 `try_lock` **确定性**地断言
  「hook 运行时锁已被持有」。
  *不*用「真的死锁」来测 —— 那是挂起,不是失败的测试。
- **studio 是否受影响**:不受影响。它的 `log_hook` 只 `emit` 一个 Tauri 事件
  (`studio.rs`),不回调宿主。

### 1.4 一个慢/卡住的工具会拖住整个宿主(已缓解,根源未解)🟡
- **现象**:`WasmHost::call_tool` 为**整个** guest 调用持有 registry 锁。于是
  一个工具在 `host.http_fetch` 里等 1.5 秒,其它 slot 的调用、以及 UI 每 5 秒一次的
  `list_tools` 轮询,都会一起等 1.5 秒。
- **实测**:槽 A 卡在 `http_fetch` 1.5 秒时,槽 B 的调用耗时 **1.5058 秒**;
  一个不回话的端点让一次无关的 `list_plugins` 在 3 秒预算内**没能完成**。
- **已修**:`host.http_fetch` 现在有**有限**超时(默认 30 秒,
  `runtime::HTTP_TIMEOUT`,可用 `Runtime::set_http_timeout` 调整)。修之前 ureq
  的默认值全是 `None`,也就是**没有**超时 —— 一个接受连接后不回话的端点会把
  **整个宿主*冻住**到天荒地老。
  回归测试:`host/tests/http_timeout.rs`(端点装死 → 调用在 1 秒超时后返回;
  正常端点仍工作)。删掉超时会让该测试真的挂起,已实测。
- **根源未解**:锁仍横跨整个 guest 调用。要真正并行,需要把
  `Arc<Mutex<Registry>>` 拆成「按 slot 加锁」,代价是:
  1. 同一 slot 的并发调用会从「串行、两个都成功」变成「`busy executing` 报错」;
  2. 跨 slot 的 `call_service` 有 AB-BA 死锁风险,需要定序或重写。
  这需要产品决策(插件到底需不需要并发),不是一次快速补丁能了的事。
  在此之前,超时只保证了「不会永久卡住」,没有保证「不会互相等待」。

## 二、中等

### 2.1 Go 插件每实例约 2.6 MB
- **现象**:Go 编译的 wasm 每个实例占 ~2.6 MB(内置调度器 + GC);Rust 只要 ~119 KB。
- **影响**:插件量大(几十上百)时不划算。
- **怎么办**:插件量大时优先用 **Rust**;或接受这个开销。

### 2.2 Go 的 GC 可能回收宿主持有的指针
- **现象**:Go 插件分配的内存,若不被 Go 自己引用,GC 可能回收 → 宿主读到坏数据。
- **本项目的处理**:示例 Go 插件把每次分配存进一个 `map`,防止被回收(见 `plugins/hello-go/main.go`)。
- **风险**:若将来 Go 引入**移动式 GC**,需要 pinning,当前方案会失效。
- **怎么办**:Go 插件作者必须自己做这个"保活";这是 Go syscall/js、wasi 类插件的通用坑。

### 2.3 服务只是"命名能力",不是共享对象
- **现象**:`provides` 只是注册一个**名字**;插件间调用通过 `host.call_service` 走 JSON,而非共享 Rust 对象。
- **影响**:不能像 dsh 那样"注入一个活的 service 对象"直接调用其方法。
- **为什么**:WASM 沙箱下,跨实例共享内存/对象不安全也不通用。
- **怎么办**:当前用"按服务名 + JSON 调用"已够用;若需要,可加更丰富的服务协议(WIT)。

### 2.4 编译缓存——已解决 ✅
- **旧现象**:进程重启后需重新编译所有 wasm(冷启动慢)。
- **现状**:已实现磁盘 `.cwasm` 缓存(P2)。`Runtime::new_cached(dir)` 开启后,
  首次写产物,二次反序列化。实测 Go 插件 **~258 ms → ~7 ms(~36x)**。
- **信任注意**:反序列化 `.cwasm` 是 `unsafe`;缓存目录必须**只有宿主可写**。

### 2.5 事件词汇是固定的 9 个
- **现象**:`turn/start` … `turn/end` 共 9 个,写死在 `hooks.rs::Event`。
- **影响**:自定义事件需要改宿主代码并重新编译。
- **怎么办**:加事件时同步改 `hooks.rs` 与 `flow.rs` 的派发点(见 [架构.md](架构.md) 扩展点)。

### 2.6 事件词汇与真实 dsh-rs 0.2.0 有偏差(实测)
- **现象**:对照 `dsh-rs 0.2.0` 实际发出的字符串,9 个事件中 **1 个对不上**:
  - 我们说 `llm/chunk`;dsh 发的是 **`assistant/chunk`**(`SessionEventData::event_type()`)。
  - dsh 另有 3 个我们**没有**的流程点:`tools/execute`、`tools/post-execute`、
    `agent/turn-stopping`。
- **影响**:若直接与 dsh 对接,`llm/chunk` 的钩子永远不会被触发。
- **已修复(P3.6)**:`Event::LlmChunk` 现序列化为 `assistant/chunk`,与 dsh 一致;
  旧名 `llm/chunk` 仍作别名接受(向后兼容)。`dsh-wasm-host` 的桥接不再需要重命名。
- **仍存在**:`tools/execute` / `tools/post-execute` / `agent/turn-stopping` 三个点未桥接。

### 2.7 `Dispatch` 丢弃了 guest 的 veto reason(实测)
- **现象**:`Registry::dispatch` 在遇到 veto 时 `break`,**不把 guest 的回复写进返回的
  `Dispatch`**;`Dispatch` 只带 `vetoed_by`,`value` 仍是原值。
- **影响**:下游无法得知**为什么**被拒;`dsh-wasm-host` 只能报一个通用 reason
  (`“denied by wasm plugin”`)而不是 guest 真实提供的那句。
- **怎么办**:给 `Dispatch` 加一个 `Option<Decision>` 或 `veto_reason: Option<String>` 字段
  (附加式、非破坏)。在此之前 `dsh-wasm-host` 不伪造理由。

## 三、轻微

### 3.1 `flow::run_turn` 是骨架,不是完整 agent
- 它只有最小循环(没有真的多步规划、没有真 LLM 流式)。
- `Model` 是 trait,真实宿主应替换 `complete()` 为真 provider 调用。
- **这是刻意的**:本项目提供"**可被介入的流程**",不提供"完整 agent"。

### 3.2 日志级别过滤——已解决 ✅
- 现可用 `log_level` 配置 / `log-level` 命令;低于阈值的记录直接丢弃。
- 默认 `debug`(保持旧行为)。

### 3.3 配置 schema 校验——已解决 ✅
- `Config::validate` / `--validate` 逐字段校验,一次报出全部问题,精确到字段。
- 仍**不是**完整 JSON Schema:只覆盖最容易静默出错的项(路径、枚举、区间)。

### 3.4 服务收敛的判定细节
- **一个 slot 可以满足自己的 inject**(它 provide 的东西,自己也"看得到")。
  这是刻意的(允许"自供自足"的插件),但可能出乎意料。
- 收敛是**同步**的:在 `load`/`unload`/`reload` 里一次性算完,不是异步滚动。

### 3.5 `Registry` 是"上帝对象"
- 它持有 runtime、shared、meta、tools、hooks、log,协调一切。
- 这是有意的(单一协调点便于推理),但也意味着它比较大。
- 若将来拆分,注意保持"跨 guest 调用不持锁"这条纪律(见 [架构.md](架构.md) §7)。

### 3.6 调整冲突是静默的 ✅【已缓解】

**现象**:两个插件若都调整同一个目标(如都 `hide` 某个贡献),**后加载者静默胜出**,
UI 上没有任何提示指出"这里有两处调整在竞争"。

**为什么这是问题**:槽位名字冲突是**报错**的(`SlotConflictError`),这是刻意的设计原则——
"两个活着的插件不能打开同一个槽位名"。但调整冲突却静默解析,
**同一个系统里两套冲突策略,是不一致的**。用户看到的结果(某个面板不见了)
无法归因到"是 A 隐藏的,还是 B 隐藏的,还是两者都在隐藏"。

**同类项目的做法可以参考**:`dsh-web` 的语义属性契约
（`packages/skins/skin-center/contracts/semantic-attrs-v1.md`）明文写着
**"契约归属：本表由皮肤中心单方面拥有和维护（冲突仲裁纪律：不靠加载顺序）"**。
也就是说,他们把那套语义属性的**所有权**交给单一持有者,用"谁拥有这个契约"来仲裁,
而不是让"谁后加载"决定。**这正是我们当前做错的地方。**

**当前缓解**:Settings 页的调整面板会列出**所有生效中的调整**及其来源,
所以信息是可见的,只是没有标出"这些调整互相竞争"。

**已做的缓解**:`SlotRegistry::adjustmentConflicts()` 检测"同一贡献被多个 owner
以同一动作调整",Settings 页新增 **Contested adjustments** 面板列出
"目标 / 动作 / 谁赢了 / 谁没生效"。

**注意这没有改变解析语义**——仍然按加载顺序、后者胜出（这是有意的:
后加载的插件应当能覆盖先前的）。**只是把静默变成可见**,让"某个面板不见了"
有据可查。

**仍待做**:把"覆盖顺序"从隐式（加载顺序）变成显式声明。可选方向是学 `dsh-web`
的"契约归属"思路——给一段 UI 定一个仲裁者,而不是纯靠加载顺序。
见 [`路线图-功能复刻.md`](路线图-功能复刻.md) 第 4.3 节。

### 3.7 调整只有声明式,没有命令式

`ui.adjusts` 只能写在 WASM 的 `ui` 块里 —— 插件**不能在运行时**根据用户操作动态调整
(比如"用户点了折叠,就隐藏某面板")。要做到那样,插件得自己控 DOM,
但那就绕过了注册表的仲裁。

**影响**:动态布局场景(可折叠、按状态显隐)目前做不了。
**这是有意的**:声明式才能保证可逆性与可组合性。若将来要命令式,
应当走"注册一组具名调整预设 + 运行时切换激活哪一个",而不是让插件直接改别人的 DOM。



### 3.8 启动偶发挂起(第三方 cordis 的 `Fiber::join`) 🟡【机制已证明,自有代码已加缓解】

**现象**:全新进程启动时,约 **1/10** 会停在 `[bundle] joining manifest` 之后不再前进。
进程内**连续多次 boot** 则 12/12 通过——只有"每个进程第一次 boot"会遇到。

**位置**:在 dsh 的 `install_base_default` 内部(`dsh-rs` 的代码,我们改不了)。

**已确认的事实**(可复现):

| 实验 | 结果 |
|---|---|
| 同一二进制、每次新进程 | ~1/10 挂 |
| 同一二进制、单进程内多次 boot | 12/12 通过 |
| 安静环境下,两种 runtime 写法 | 各 60/60 通过 |
| **20 个满载进程时** | 两侧都挂(各 ~3%) |

**与 runtime 来源无关——更正记录**。本条目最初写着"借用
`tauri::async_runtime::handle()` 再 `block_on`"会挂、而"显式 `new_multi_thread()`"
通过,并据此把 examples 改成了显式 runtime。

**那个结论是被污染的环境误导的**:当时我在后台并行跑 cargo 构建,
"显式"那一组恰好跑在低负载窗口里。受控重测(交替 A/B、消除负载漂移)
后两种写法的差异**消失了**;人为加 16~20 个满载进程后,**挂起在两侧随机出现**,
方向每次不同:

| 条件 | `tauri-handle` | `explicit` |
|---|---|---|
| 安静 | 60/60 | 60/60 |
| 4 个满载进程 | 40/40 | 40/40 |
| **16 个满载进程** | **60/60** | **58/60** |
| **20 个满载进程** | **97/100** | **97/100** |

所以:**触发条件是负载,不是 runtime 的来源。**

**但这不影响 examples 的改动仍然正确**:在 Tauri app 之外,`handle()` 会懒建一个
全局 runtime 并返回它自己的 handle,然后我们 `block_on` 这个 handle——
**主线程阻塞在自己的 runtime 上**。这是自引用,是个**独立的、应当避免的缺陷**
(即使它不导致这个挂起)。examples 持有自己的 runtime 依然是对的。

**挂起究竟发生在哪一行(已定位)**:抓到的 5 次挂起里,4 次停在
`[bundle] joining manifest` 之后,1 次停在 `[bundle] joining agent-loop` 之后。
那两行是 **dsh-rs 自己打的**(`bundle/mod.rs:226`),而它紧接着调用的就是:

```rust
// dsh-rs-0.2.0/src/bundle/mod.rs:225-229  —— 不是我们的代码
for handle in &handles {
    eprintln!("[bundle] joining {}", handle.name());
    handle.join().await   // ← 卡在这里；join() 由 cordis 实现
        .map_err(...)?;
}
```

所以责任分层是:**机制**在 cordis(**已证明**,见下),**调用点**在 dsh-rs 的
无限等 `join()`,而**我们能改的只有自有的两处**(已改,见末尾)。

**机制(已证明,与上面的端到端定位独立):**

cordis `Fiber::join` 的等待顺序是:

```rust
let busy = { /* 读 driver.dirty / task.is_finished() / loaded != desired */ };
if !busy { break; }
let _ = rx.borrow_and_update().clone();   // ← 把【当前】值标记为已见
if rx.changed().await.is_err() { break; } // ← 却等【下一次】变化
```

`tokio::sync::watch` 的语义我用三种顺序直接验证过:

| 顺序 | 结果 |
|---|---|
| **`bump` → `borrow_and_update` → `changed`** | **永久挂起** ← **cordis 用的是这个** |
| `borrow_and_update` → `bump` → `changed` | 正常唤醒(正确顺序) |
| `bump` → `changed`(不 snapshot) | 正常唤醒 |

即:`borrow_and_update()` **消费掉**了那次 bump,紧随的 `changed()` 等的是一个
**永不再来**的变化。**所以只要有一次 settle 通知落在"读 busy"与"注册快照"之间,
`join()` 就永久挂起。** 这是机制层面的确证(顺序 A 稳定复现)。

**但端到端因果仍未坐实**:我写的最小 cordis 复现(插件在 join 的同时结清)
**2000 次迭代 0 次超时**。现在的线索是**窗口需要真实的线程竞争才够宽**——
安静环境下 240 次全过,加 16~20 个满载进程后才稳定出现。
所以"这就是那次 ~1/10 挂起的原因"是**强怀疑 + 一致的现象证据**,
但**不是已证的因果**。写清楚这一点,免得下一个人以为它已被完全坐实。

**已加的缓解**(不依赖上述怀疑是否成立):我们自己代码里原本直接用无界的 `fiber.join()`
(桥和每个 slot)。现在统一走 `join_bounded`,它**轮询 lock-free 的 `Fiber::state()`**
(原子镜像,每次状态转换都会重发布),而不是信任通知——**轮询不会漏掉转换**,
因为正确性依赖"当前状态",不依赖"观察到了每一次变化"。

超时**不算错误**:仍处于 `Pending`(等在某个服务上)是受支持的状态,记日志后继续。
只有真正 `Failed` 才报错。

**为什么不用 `join_with_timeout`**:它的等待顺序与 `join()` **相同**(同样先 busy、
再 snapshot、再 changed),只是多了一层超时——所以它在竞态下会**报超时错误**而不是挂起。
那对我们没用,因为"还没收敛"是合法状态,我们不想把它变成错误。
轮询 `state()` 两个问题都没有。

**修这个缓解时踩到的坑**:第一版轮询让 `Pending` 也走等待分支 → **每个 pending 插件挂载都要 10 秒**
(实测 10.03s)。因为"injects 未满足"的插件会**一直**是 Pending。
改成 `Pending` 立即返回后降到 **19.7ms**。

**上游**:`cordis-rust 0.2.1`(`github.com/redoop/cordis-rust`)。若要彻底解决,
应向该仓库报告,或改用轮询式的等待(我们已在自有代码里这么做)。

## 四、设计取舍记录(为什么这么做)

| 决定 | 理由 |
|---|---|
| **用 WASM 而不是 dlopen** | dlopen 无法真卸载(代码段永久驻留)、崩溃会带崩宿主;WASM 真隔离 + 真卸载 |
| **JSON-over-linear-memory 作 ABI** | 任何语言都能实现;不绑定 Rust/Component Model,先解决"能用" |
| **日志改用 WASI stdout/stderr** | `host.log` 要求手写胶水,JS/Python 几乎做不到;所有语言的 print 都走 WASI |
| **fail-open 的钩子** | 一个坏钩子不该卡死整个流程 |
| **原子热更新(stage-then-commit)** | 坏构建绝不能拖垮在跑的插件,这是安全底线 |
| **slot 作为稳定身份** | 插件内部改名/重建不该让热更新失去目标 |
| **池化分配器可选** | 按需分配足够简单;大量实例时才需要池化 |
| **notify 而非轮询** | 延迟从“轮询间隔”降到“事件延迟”(实测 ~136ms vs 30s) |
| **服务收敛用不动点迭代** | 自然的级联语义;一趟点亮整条链 |
| **跨调用时把插件取出** | 唯一能同时做到“嵌套安全 + 不死锁”的简单办法 |
| **用新 crate 组合 dsh 而非改 host** | dsh 已是完整 cordis 内核 + agent harness;WASM 运行时作为插件**插进去**,而不是在 Tauri 层重写编排 |

## 五、如果遇到问题先看这些

| 症状 | 先看 |
|---|---|
| 插件加载失败 | [ABI.md](ABI.md) 的必需导出清单 |
| 插件加载了但工具不可见 | 它可能 **quiescent**(inject 未满足)→ 看 `plugins` 命令 |
| 日志不出来 | 日志走 WASI stdout/stderr;确认宿主 `echo_stderr` 或读 `LogHook` |
| 改了 wasm 没热更新 | 确认 `watch.enabled`,或手动 `reload <slot>`;缓存按 mtime |
| Go 插件报未初始化 | 确认宿主调用了 `_initialize`(当前版本已处理) |
| 死循环插件卡住宿主 | **当前无 fuel 限制** → P0 会解决;临时对策:去掉该插件 |
| 热更新后服务依赖错乱 | 看 `reload_respects_service_graph` 的语义;收敛是同步重算的 |
| dsh 的 chunk 钩子不触发 | 已对齐:`assistant/chunk`(旧名 `llm/chunk` 仍可用)→ §2.6 |
| wasm 插件的 veto 理由丢了 | 宿主 `Dispatch` 不带 reason → 见 §2.7 |
