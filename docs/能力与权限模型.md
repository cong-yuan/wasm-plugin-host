# 能力与权限模型

> 本文定义 wasm-plugin-host 的长期安全边界。目标不是改变现有插件体系，而是在保持
> `trusted` 兼容模式的同时，引入可以承载第三方插件的 `sandboxed` 模式。

## 1. 设计目标

1. **默认拒绝、显式授予**：第三方插件没有声明/没有被宿主授予的能力不可用。
2. **能力与资源统一建模**：文件、网络、Agent 流程、Service、UI、CPU/内存/时间预算都进入同一权限模型。
3. **不破坏现有可信插件**：现有插件可继续以 `trusted` 运行；迁移期不要求立即重写。
4. **权限由宿主强制执行**：manifest 只是请求，不是授权。最终授权集由宿主策略计算。
5. **可审计、可解释**：宿主能回答“这个插件为什么能访问这个资源/拦截这个事件”。
6. **为 Component Model/WIT 留路**：v1 可继续 JSON over linear memory，能力边界不绑定 ABI 编码。

## 2. 两种运行档位

### 2.1 `trusted`

兼容当前行为，适用于自己维护、随 App 一起发布的插件。

- 可保留完整 WASI preopen 与现有 `host.*` 导入。
- 仍受资源预算保护（建议至少启用调用超时；fuel/内存上限可配置）。
- UI 插件可以使用宿主明确开放的前端桥。
- **不得作为第三方 Marketplace 的默认档位。**

### 2.2 `sandboxed`

第三方插件的标准运行档位。

- 文件系统默认不可见。
- 网络默认不可用。
- Agent Hook 默认不可订阅。
- Service 默认不可消费/提供。
- UI 默认不可挂载。
- 必须有 CPU、内存、调用时限。
- 所有高权限动作经过 capability gate。

迁移阶段建议：旧配置缺少 `trust` 时按 `trusted` 解释并打印迁移警告；新创建的第三方插件配置默认 `sandboxed`。等生态迁移完成后，再考虑把全局默认改成 `sandboxed`。

## 3. 配置模型

建议把“插件声明的请求”和“部署环境授予的权限”分开。

插件声明（随插件发布）：

```json
{
  "name": "repo-assistant",
  "abi": 1,
  "capabilities": {
    "filesystem": {"read": ["workspace/**"]},
    "network": {"allow": ["api.github.com"]},
    "agent": {
      "observe": ["assistant/chunk"],
      "rewrite": ["agent/request"],
      "veto": ["tools/pre-execute"]
    },
    "services": {"consume": ["memory"], "provide": ["repo-index"]},
    "ui": {"slots": ["sidebar"], "routes": ["/repo"]}
  }
}
```

宿主配置（部署者授权）：

```json
{
  "plugins": {
    "repo": {
      "path": "plugins/repo.wasm",
      "trust": "sandboxed",
      "grant": {
        "filesystem": {"read": ["${workspace}/**"]},
        "network": {"allow": ["api.github.com"]},
        "agent": {
          "observe": ["assistant/chunk"],
          "rewrite": ["agent/request"],
          "veto": ["tools/pre-execute"]
        },
        "services": {"consume": ["memory"], "provide": ["repo-index"]},
        "ui": {"slots": ["sidebar"], "routes": ["/repo"]}
      },
      "limits": {
        "memory_mb": 64,
        "fuel": 200000000,
        "call_timeout_ms": 5000,
        "max_concurrent_calls": 1
      }
    }
  }
}
```

最终有效能力：

```text
effective = requested ∩ granted ∩ host_policy
```

任何一层没有允许，都视为拒绝。

> Phase A 当前已经实现 `requested ∩ granted`；全局 `host_policy` 这一层暂时等价于“无额外收窄”，接口语义已预留，后续可在企业策略/Marketplace 策略接入时增加第三层过滤。

### 3.1 启动阶段规则

ABI v1 当前的生命周期顺序是 `plugin_init → plugin_configure → plugin_describe`。因此对
`host.http_fetch` 等**宿主中介能力**，`sandboxed` 在 `plugin_describe` 返回 capability request
之前保持默认拒绝，描述完成后才计算 `requested ∩ granted`。

WASI p1 文件系统是一个例外：preopen 必须在实例创建前确定，而 capability request 要到
`plugin_describe` 才可见。因此直接 WASI 只开放 `read` preopen，并以**宿主 grant 本身**作为安全上限；插件 request 不作为这条路径的安全边界。

`write/create/delete` 不映射到 WASI `MUTATE`。它们通过 `host.fs_op` 执行，并恢复标准的 `requested ∩ granted` 语义：宿主在实例建立时把 mutation grant root 固化成 `cap_std::fs::Dir` 句柄，调用只接受该 root 下的相对路径，拒绝绝对路径和 `..`。

`trusted` 兼容模式保持原有完整 root preopen 行为。

## 4. Capability 分类

### 4.1 文件系统

```text
filesystem.read
filesystem.write
filesystem.create
filesystem.delete
```

要求：

- `sandboxed` 下不再 preopen `/`。
- Phase B 已用 WASI Preview 1 preopen 落地 `filesystem.read` 目录白名单。
- `write/create/delete` 通过 `host.fs_op` + cap-std 目录句柄执行，不用粗粒度 WASI `MUTATE` 冒充细粒度授权。
- WASI preopen 本身使用 capability filesystem API 阻止通过 `..` 逃逸；配置/加载层要求绝对路径、canonicalize 成功且目标为目录，并拒绝父子目录同时作为独立 preopen root。
- WASI 直通保持 read-only；mutation 统一走 `host.fs_op`，`write_file` 不隐式 create，create/delete 分权。
- 长期优先 `host.fs.*` / WIT capability API，而不是裸露大范围 WASI。

### 4.2 网络

```text
network.http
network.hosts[]
network.methods[]
```

要求：

- `host.http_fetch` 必须读取当前插件的 effective capability。
- 域名精确或受控通配；禁止插件自行绕过代理。
- 限制响应体大小、重定向次数、连接/读取超时。`sandboxed` 禁止客户端自动跟随 30x：下一跳必须由插件重新调用 `host.http_fetch`，因此会再次经过 host/method Capability Gate；`trusted` 保留兼容重定向行为。
- IP literal、localhost、link-local、metadata endpoint 等按敏感目标处理：普通 wildcard 不得授权，必须使用 exact host grant。当前实现已覆盖 IP literal、`localhost`/`.localhost` 与常见云 metadata host；这能防止 `*` 意外获得 SSRF 权限。
- 将来若开放 WASI socket，必须复用同一授权模型，不能成为旁路。
- DNS rebinding 第一层也已接入 resolver：`sandboxed` 会过滤解析结果中的 loopback/private/link-local/unspecified/multicast 等敏感 IP；只有该 IP 本身也在 effective grant 中才允许 connect。也就是说，`internal.example.com` 即使被授权，若解析到 `10.0.0.8`，仍需要显式授权 `10.0.0.8`。resolver 返回的就是过滤后的 socket 地址，因此 resolve policy 与 connect 使用同一地址集合。
- resolver 对敏感 resolved IP 的 allow/deny 也写入宿主 `AuditSink`，capability 名为 `network.resolve`；因此网络失败不再只有模糊的 `host not found`，宿主可追溯到具体 IP 的权限决策。

### 4.3 Agent 流程

Agent Hook 是高权限能力，必须按“事件 + 动作”授权：

```text
agent.observe[event]
agent.rewrite[event]
agent.veto[event]
```

加载阶段校验：事件存在、动作被事件契约允许、effective capability 已授权。失败应在插件激活前返回明确错误。

## 5. Hook 契约

每个事件由宿主维护稳定 `EventSpec`，而不是只维护字符串：

```text
EventSpec {
  name,
  payload_schema,
  allowed_actions: observe | rewrite | veto,
  failure_policy,
  timeout_class,
  ordering
}
```

推荐事件命名空间：`turn.*`、`agent.*`、`model.*`、`assistant.*`、`tool.*`、`session.*`、`ui.*`、`system.*`。

规范：

- observe 返回值永远不改变流程。
- rewrite 必须通过事件 payload schema 校验。
- veto 只允许在 EventSpec 明确允许的事件上发生，reason 必须保留并传给上层。
- 默认 fail-open；未来安全关键事件可配置 fail-closed。
- Hook 同样受调用预算限制。
- priority 只负责排序；同 priority 使用稳定 slot 顺序。

## 6. Service 权限

现有 `injects/provides` 继续作为依赖图，但加入：

```text
services.consume[]
services.provide[]
```

未授权 provide 的 service 不注册；未授权 consume 的 `host.call_service` 直接拒绝。Service 名只是 capability 名，不意味着可信。未来 WIT 化时保持 capability 语义不变。

## 7. UI 权限

UI capability 至少区分：

```text
ui.slots[]
ui.routes[]
ui.windows
ui.theme
ui.adjusts[]
ui.backend_commands[]
```

原则：

1. 插件前端不能直接获得完整 Tauri invoke 面。
2. 父页面暴露受控 Plugin Bridge，按插件身份和 capability 过滤命令。
3. iframe/webview 必须绑定插件 identity；消息中的 source 字符串不能作为授权依据。
4. `ui.adjusts` 是高权限能力，应独立授权。
5. 路由、槽位、主题等在安装/加载时校验，运行时只使用已批准 registry。

## 8. 资源预算

最低预算：

```text
memory_mb
fuel
call_timeout_ms
max_concurrent_calls
max_output_bytes
max_log_bytes_per_call
```

`sandboxed` 必须有安全默认值。超限只终止当前调用/插件，不让宿主进程失稳；错误要能区分 permission denied / fuel exhausted / memory limit / timeout。

## 9. HostState 与执行路径

建议加入不可变授权快照：

```rust
pub struct HostState {
    pub wasi: WasiP1Ctx,
    pub policy: PluginPolicy,
    pub capability_gate: CapabilityGate,
    // config / log / services / identity 等现有字段...
}
```

所有 `host.*` 导入通过统一 gate：

```text
guest -> host.http_fetch
          |
          +-> CapabilityGate::require(NetworkHttp, target)
          +-> Budget::check(...)
          +-> execute
          +-> AuditSink
```

权限判断不要散落在调用点，应由一个可测试的 `CapabilityGate` 统一执行。

## 10. 审计

至少记录 timestamp、plugin/slot、capability、resource/event、allow/deny、reason、duration。默认不记录敏感正文、token、文件内容。

## 11. 与 ABI v1 的关系

这不是 ABI v2。ABI v1 的导出函数和 JSON 编码可以保持不变；Capability 是 host policy + runtime contract。将来迁到 Component Model/WIT 时，把同一 capability 模型映射成类型化接口即可。

## 12. 实施顺序

### Phase A — 安全地兼容现状
- 新增 `trust: trusted | sandboxed`。
- 把现有 full WASI 行为明确收进 `trusted`。
- 新增 `EffectiveCapabilities` / `CapabilityGate`。
- `host.http_fetch` 先接入 gate。
- 配置校验支持 `grant` / `limits`。

### Phase B — 真沙箱（实现中）
- [x] `sandboxed` 默认无 root preopen。
- [x] `filesystem.read` WASI 目录白名单；`write/create/delete` 由 `host.fs_op` + cap-std capability handles 细粒度执行。
- [x] mutation path 必须相对 root、禁止 `..`/绝对路径；file payload decoded 上限 16 MiB；create/write/delete 正负与审计测试代码已补。
- [x] fuel、StoreLimits 内存上限、epoch 调用超时。
- [x] `max_concurrent_calls` 不伪装成已实现并发池：当前单实例/slot 架构下 sandboxed 只接受 `1`，更大值加载前拒绝。
- [x] output cap；`max_log_bytes_per_call` 按每次 guest 调用累计限制日志字节。
- [x] fuel / memory / output / timeout 测试代码。
- [x] sandboxed `host.log` + WASI stdout/stderr 共用同一调用级日志预算，每次顶层 guest 调用重置。
- [x] filesystem grant 加载前要求绝对路径、可 canonicalize、且目标为目录。
- [x] `path_open` 正反向测试代码：read grant 内文件可打开，无 filesystem grant 时失败。
- [x] Rust 工具链验证已恢复；host / dsh 全量测试已通过。两个大 UI shell 的真实 `wasm32-wasip1` sandboxed load 还额外验证了默认 fuel 预算。
- [x] 重叠 read preopen root 诊断：父子目录同时作为 WASI read root 时加载拒绝；mutation root 由 `host.fs_op` 显式 root 选择，不依赖 preopen 合并。

### Phase C — Agent / Service / UI capability（主体已落代码）
- [x] sandboxed `injects` → `services.consume` request ∩ grant 校验。
- [x] sandboxed `provides` → `services.provide` request ∩ grant 校验。
- [x] `host.has_service` / `host.call_service` 运行时再次检查 consume capability。
- [x] Observe hook → `agent.observe(event)`；Waterfall 当前可同时 rewrite/veto，因此加载时要求两项 capability。
- [x] UI slots/routes/windows/adjusts 与 assets 加载门禁。
- [x] `ui.theme` / `ui.backend_commands` 已有运行时 CapabilityGate 入口；Registry 还提供 typed `UiHostAction` 供真实 frontend host 统一授权。
- [x] EventSpec 已区分 observe-only / rewrite / veto；dispatch 会忽略事件不允许的动作，capability 也只要求该事件真实支持的动作。
- [x] veto reason 保留到 `Dispatch` / `TurnOutcome` / dsh bridge。
- [x] EventSpec 已进入 dispatch 强制执行。

### Phase D — UI capability
- [x] Registry 已提供宿主强制执行 seam：`authorize_ui_action(authenticated_slot, action)`，
  action 使用 `UiHostAction::{BackendCommand, Theme, Adjust, ProvideSlot, InjectSlot, RenderSlot, OpenWindow, CloseWindow}`；
  旧的细粒度 authorize 方法仍可直接使用。所有路径复用同一 CapabilityGate + AuditSink。
- [x] `OpenWindow` 运行时除 `ui.windows` 外还校验窗口名确实存在于该插件自己的 `UiDecl.windows`，避免一个布尔 capability 放大成任意窗口名。
- [x] `ProvideSlot` / `RenderSlot` 必须命中插件自己的 `UiDecl.provides`；`InjectSlot` 必须命中 `UiDecl.injects`。grant 可以收窄 manifest，但不能把 manifest 在运行时扩张。
- [x] `Adjust` 同样必须匹配插件自己的 `UiDecl.adjusts` pattern；host grant 中额外存在的 adjustment pattern 不会自动扩张插件运行时可调整的 UI 面。
- [x] 运行时 UI 动作因 manifest 未声明而被拒绝时，同样写入 AuditSink（`ui.slots` / `ui.windows` deny），不会成为审计盲区。
- [x] Registry 提供 `slot_effective_capabilities(slot)` 只读快照。sandboxed 返回真正的 request ∩ grant，trusted 明确标记 `unrestricted=true`；前端宿主不应拿 `slot_policy().grant` 代替 effective capability。
- [x] `UiHostAction` JSON 使用 `deny_unknown_fields`；payload 自报 `plugin_id` 等身份字段会解码失败，authenticated slot identity 只能由宿主上下文提供。
- [x] Registry 提供 `parse_and_authorize_ui_action(authenticated_slot, payload)`：严格解码 + 授权一次完成，并返回已验证的 typed action，避免不同 frontend host 重复实现 parse/auth 规则或授权后再次读取原始 payload。
- [x] typed action 携带执行所需数据：`BackendCommand.args`、`OpenWindow.params` 都在授权前进入同一个严格解码对象；授权完成后宿主无需、也不应再次读取 raw message。
- [ ] 前端 Plugin Bridge 替代完整 Tauri invoke。真实 Studio/Tauri 前端宿主源码不在
  本仓库，因此这里不伪造 JS-only 安全边界。
- [x] `hana-shell` / `openhanako-shell` manifest 已声明自身 UI slot/window 与实际使用的 backend command request，可在 sandboxed 模式下由宿主 grant 精确收窄。
- route/slot/window/theme/adjusts 分权。
- 插件 identity 与后端授权绑定。

### Phase E — 类型化能力接口
- Component Model / WIT。
- `host.fs` / `host.net` / service WIT。
- 保留 capability 名称与授权语义，只替换传输层。

## 13. Definition of Done

- [x] 无授权读 `/etc/passwd` 被拒绝（Unix 真实路径反向测试）。
- [x] workspace / 显式 read preopen 外路径被拒绝。
- [x] 未授权域名的 `http_fetch` 被拒绝。
- [x] 未授权 Hook 不能注册 observe/rewrite/veto。
- [x] 未授权 service 不能 consume/provide。
- [ ] UI 插件不能直接调用未授予的 Tauri command。
- [x] 死循环被 fuel/timeout 中止。
- [x] 内存增长被限制。
- [x] trusted 旧插件仍可按兼容模式运行。
- [x] Capability allow/deny 与 fuel/memory/timeout/output/log 超限进入独立有界 AuditSink，并有查询 API / 测试断言。

审计流与插件日志分离，由宿主持有；HTTP 审计只保存 method + host，不保存 URL path/query，避免把 access token 等参数复制进审计记录。Registry 暴露 `audit_events()`、`audit_events_for(slot)`、`audit_events_since(seq)`。
