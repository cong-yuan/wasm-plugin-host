## P0 —— 权限 / 能力模型 🔴

**为什么最重要**:当前插件拿到**完整 WASI**(能读写任意文件、访问网络)。
这意味着现在**不适合跑第三方不可信插件**。不解决这个,这个宿主只能用于"自己写的、可信的"插件。

### 要做的事

1. **收窄 WASI 上下文**
   - 默认**不给**任何文件系统/网络能力
   - 用 `WasiCtxBuilder` 的 preopen 白名单:`--allow-dir <path>` 才暴露目录
   - 网络:默认关闭(需要则显式开启并限目标)

2. **资源上限**
   - **fuel**:限制指令数(防死循环);`Config::consume_fuel(true)` + `Store::set_fuel`
   - **内存上限**:限制线性内存增长(`StoreLimits` / 池化的 `max_memory_size`)
   - **时间上限**:调用级超时

3. **配置化的能力声明**
   - 配置文件每个插件单元增加 `permissions` 字段:
     ```json
     "greet": {
       "path": "...",
       "permissions": {
         "read_dirs":  ["/tmp/sandbox"],
         "write_dirs": ["/tmp/sandbox"],
         "network":    false,
         "max_memory_mb": 64,
         "max_fuel": 100000000,
         "timeout_ms": 5000
       }
     }
     ```
   - 无 `permissions` → 默认**最小权限**(什么都不给)

4. **能力 API**(可选,更细粒度)
   - 用 `host.fs_read` / `host.net_fetch` 这类显式导入替代裸 WASI
   - 宿主在这些导入里做路径校验与限流

### 验收标准

- [ ] 一个"恶意"插件尝试 `open("/etc/passwd")` → 返回权限错误,**不是**成功
- [ ] 一个死循环插件 → 在 fuel 耗尽后**被终止**,宿主不受影响
- [ ] 一个疯狂分配内存的插件 → 在内存上限处失败,宿主 RSS 不飙升
- [ ] 配置 `permissions.read_dirs: ["/tmp/x"]` 后,插件**只能**读 `/tmp/x`
- [ ] 新增测试:`permission_denied_without_grant`、`fuel_exhaustion_terminates_plugin`、
      `memory_limit_enforced`、`preopen_whitelist`
- [ ] 文档:在 [ABI.md](ABI.md) 与 [使用指南.md](使用指南.md) 增加"权限"章节

### 风险 / 注意
- WASI p1 的能力模型本身较粗(基于 preopen fd);细粒度需要自定义导入
- fuel 会带来性能开销,默认应关闭、按插件开启

## P1 —— Tauri 集成 🟡

**为什么**:这是这个宿主**真正落地到你的 App** 的一步。目前是独立 CLI + 库。

### 要做的事

1. **把 `Registry` 作为 Tauri managed state**
   ```rust
   .manage(Mutex::new(HostState { reg, sup }))
   ```

2. **暴露一组 `#[tauri::command]`**
   | 命令 | 作用 |
   |---|---|
   | `list_plugins()` | 列出 slot / 状态 / 工具数 / active |
   | `list_tools()` | 列出工具 |
   | `load_plugin(slot, path)` | 加载 |
   | `unload_plugin(slot)` | 卸载 |
   | `reload_plugin(slot)` | 热更新 |
   | `set_plugin_config(slot, json)` | 改配置并应用 |
   | `call_tool(tool, args)` | 调用 |
   | `get_logs(since_seq)` | 拉日志(增量) |
   | `enable/disable_plugin(slot)` | 开关 |

3. **日志转发到前端**
   ```rust
   let hook: LogHook = Arc::new(move |rec: &LogRecord| {
       // 通过 Tauri 的 emit 发到前端
       let _ = app_handle.emit("plugin-log", rec);
   });
   let reg = Registry::with_logging(rt, 1000, false, Some(hook));
   ```

4. **前端**:一个插件管理面板(列表 + 开关 + 热更新按钮 + 日志流)

### 验收标准

- [ ] 一个最小 Tauri App:前端按钮能 load/unload/reload 插件
- [ ] 前端能实时显示插件日志(订阅 `plugin-log` 事件)
- [ ] 改配置文件后,前端状态自动刷新
- [ ] 文档:Tauri 集成示例放 `examples/tauri-app/` 或在 README 给最小代码

### 依赖
- 建议先做 P0(权限)再接 Tauri —— 否则前端能把任意 wasm 跑满权限

## P2 —— 磁盘编译缓存 🟡

**为什么**:当前只在**进程内**缓存编译结果。冷启动时每个插件都要重新编译(几十到几百 ms)。

### 要做的事
- 用 `Engine::precompile_module(bytes) -> Vec<u8>`,写到 `<cache>/<hash>.cwasm`
- 启动时 `Module::deserialize(bytes)`,**毫秒级**加载
- 缓存键:wasm 内容 hash + 引擎配置 hash(引擎配置变了要失效)
- 配置项:`cache_dir`、开关

### 验收标准

- [ ] 首次启动:编译;二次启动:直接从 `.cwasm` 反序列化
- [ ] 实测冷启动加速(记录轮次:编译 vs 反序列化)
- [ ] 引擎配置变化(如开了 fuel)→ 缓存自动失效
- [ ] 新增测试:`disk_cache_roundtrip`、`stale_cache_invalidated_on_engine_change`

## P3 —— 增强项 🟢

### P3.1 工具级依赖编排
- 现在已有 tool/hook/service。可加"工具依赖工具"(A 的工具需要 B 的工具先可用)
- 或"工具提供/消费"更细的图
- **验收**:一个带依赖的工具链能自动排序/激活

### P3.2 JS / Python(Component Model)
- `Runtime` 是唯一知道"core module"的地方 —— 加 `ComponentBackend` 即可
- JS 用 `jco`、Python 用 `componentize-py`,产出 **Component** 而非 core module
- ABI 从"JSON over linear memory"换成 **WIT 类型化接口**
- **Registry / Plugin 生命周期层完全不变**
- **验收**:一个 JS 写的插件能加载、能出日志、能被调用

### P3.3 日志级别过滤
- 配置文件加 `log_level`;低于阈值的记录丢弃
- CLI `logs --level warn`
- **验收**:`log_level: "warn"` 时 debug/info 不出现

### P3.4 配置 schema 校验
- 配置加载时校验字段(路径存在性、枚举值)
- 错误信息精确到字段
- **验收**:坏配置给出明确错误而非静默忽略

### P3.5 `notify` 之外的 .watcher 优化
- 目前 notify + 80ms 去抖已够用
- 可选:批量事件合并、inotify 溢出处理

## 建议的执行顺序

```
P0 权限模型 ────────────┐
                        ├─→ P1 Tauri 集成 ─→ (产品可用)
P2 磁盘缓存(可并行)──┘
                        
P3 各项按需
```

**理由**:
- P0 是**安全前提**,应先于任何"开放插件"的场景
- P1 是**落地**步骤,让宿主真正进 App
- P2 独立,可与 P0/P1 并行,收益是启动速度
- P3 都是锦上添花
